# Web Push Notifications (Browser Push)

Customer-facing browser push for the commission lifecycle. Shipped 2026-09-21.

## Scope (v1)

- **Audience**: customers of a studio (signed-in `customers`), notified even when the tab is closed.
- **Events**: customer-facing `payment_success`, `progress_update`, `commission_finished`, `chat_message` (artist replies) — plus studio-facing (Phase B) `chat_message` (customer writes), `commission_submitted`, `payment_received`, delivered to every artist/admin user of the tenant.
- **Not yet**: shop/library/tips events, per-event preference UI.
- Push is an engagement layer, not an email replacement: email remains the always-works channel, and on iOS push only reaches users who installed the site (see iOS caveat).

## Architecture

```
commission hook / artist action
  └─ queueOrSendCommissionPush()                src/lib/push/queue.ts
       ├─ QStash configured → publishJSON ({ type, commissionId, customerId, tenantId, queueItemId })
       │     → POST /api/webhooks/push          (signed; mirrors /api/webhooks/email)
       └─ otherwise → direct send
            └─ deliverCommissionPush()          src/features/push/actions/deliver-push.action.ts
                 ├─ resolve studio (subdomain/customDomain/logo, depth 1)
                 ├─ buildCommissionPushPayload()        src/lib/push/payload.ts  (pure, tested)
                 └─ deliverPushToUser()
                      ├─ payload.find push-subscriptions (polymorphic user + tenant)
                      ├─ sendWebPush() per endpoint     src/lib/push/send.ts    (web-push, VAPID)
                      └─ bookkeeping per outcome:
                           sent        → lastSuccessAt, failureCount 0
                           gone (404/410) → delete row (endpoint retired by the push service)
                           failed      → failureCount++, lastError; deleted at 10
```

Chat + studio events (both directions):

```
ChatMessages afterChange (operation === 'create')
  ├─ author.role 'artist'   → queueOrSendChatPush() → deliverChatPush() → room customer
  └─ author.role 'customer' → queueOrSendTenantArtistPush() → deliverTenantArtistPush()
                                                                   └─ every user with `tenants ∋ tenant`
Commission hooks (notifyDiscordOnSubmission / notifyDiscordOnPaymentSuccess)
  └─ queueOrSendTenantArtistPush() → tenant artists
Common: deep links /chat/<roomId> or /dashboard/commission/<id>
        bodies deliberately generic for chat ("Open the chat to read it.") — no message text on lock screens
```

### File map

- `src/collections/PushSubscriptions.ts` — `push-subscriptions` collection (polymorphic `user` → `users`/`customers`, `tenant`, unique `endpoint`, keys, origin, failure bookkeeping). Access: own rows or admin; `associateTenant` fills tenant from the request subdomain for customer-initiated rows. `endpoint`, `keys.*` and `userAgent` carry field-level validators (`src/lib/push/validation.ts`): REST/GraphQL are enabled by default and `create` access only requires writing your own row, so the allowlist must hold at the data layer, not only in `subscribeToPush`.
- `src/lib/push/vapid.ts` — VAPID config from env; `isPushConfigured()` gates the whole feature (unconfigured = silently off, like the email/QStash fallbacks).
- `src/lib/push/validation.ts` — zod input schema for the subscribe action, the endpoint allowlist (fcm.googleapis.com, `*.push.services.mozilla.com`, `*.push.apple.com`, `*.notify.windows.com`), and the field validators the collection runs on every write path. The endpoint is a capability URL we later POST to — the allowlist is the SSRF guard, enforced on write *and* re-checked in `sendWebPush` before dialling.
- `src/lib/push/payload.ts` — copy + deep links for the commission, chat, and studio-event builders (mirrors `src/lib/email.ts` conventions: progress → `/queue/<queueItemId>`, payment/finished → `/dashboard/commission/<id>`; chat → `/chat/<roomId>`).
- `src/lib/push/send.ts` — web-push wrapper; classifies results, never throws.
- `src/lib/push/queue.ts` — QStash-or-direct, mirrors `queueOrSendCommissionEmail`.
- `src/features/push/actions/*` — `subscribeToPush`, `unsubscribeFromPush`, `deliverCommissionPush` / `deliverChatPush` / `deliverTenantArtistPush` / `deliverPushToUser`.
- `src/collections/hooks/notifyOnChatMessage.ts` — chat trigger both directions: artist creates push the room customer, customer creates push the tenant's artists.
- `src/components/push/usePushSubscription.ts` — shared client state machine (detect / request / subscribe / cleanup) used by both opt-in surfaces.
- `src/components/admin/ArtistPushToggle.tsx` — compact artist opt-in in the admin header (Phase B); VAPID key fetched from `/api/push/config`, hidden off studio hosts and on iOS Safari.
- `src/app/api/push/config/route.ts` — exposes the VAPID public key to the admin toggle (public key only).
- `src/app/api/webhooks/push/route.ts` — QStash receiver (signature-verified, unknown types acknowledged).
- `public/sw.js` — service worker: `push` → `showNotification`, `notificationclick` → focus an existing tab or open the deep link (targets are re-anchored to the SW's own origin; matching is by pathname, so scheme/host spelling can never spawn a new tab per click). **No caching by design** (the site owns its caching strategy).
- `src/components/push/PushSubscribeBar.tsx` — opt-in UI (client component). Mounted for signed-in customers on high-intent surfaces: the queue board (`QueueContent`, `status` mode keeps the on/off control visible), the commission detail page, and the customer commission dashboard (`cta` mode hides entirely once subscribed).
- `src/app/manifest.ts` + `src/app/apple-icon.png` — PWA manifest and iOS home-screen icon (installability is a prerequisite for iOS push).
- `scripts/generate-vapid-keys.mjs` — keypair generator (`yarn push:generate-keys`).

## Data model & multi-origin reality

Subscriptions are **per origin**: a browser registered on `studio-a.2monke.com` produces an endpoint tied to that origin's service worker, independent of the platform root and of other studios. Rows therefore store `tenant` + `origin`, and delivery filters by **(user, tenant)**. One backend sends to all endpoints; notifications display the studio's branding because the payload carries the studio logo and a studio deep link. Same browser, second studio → a second row (opt-in there too). Per-user cap: 10 newest rows kept (`pruneOldSubscriptions`).

## Environment & keys

```
VAPID_PUBLIC_KEY=...      # from `yarn push:generate-keys`
VAPID_PRIVATE_KEY=...     # treat as permanent — rotation invalidates every stored subscription
VAPID_SUBJECT=mailto:...  # contact for push service operators
```

One keypair covers every host (platform root + all subdomains): the key identifies the sending application server, not the origin. `.env.example` documents the block; dev keys were generated into the local `.env` when the feature was built. Local QStash is unset → dev/test take the direct-send path.

## Client behavior

- The bar renders nothing until it can decide a state; the permission prompt fires only from an explicit click (Safari requires a gesture; Chrome auto-blocks after repeated first-load prompts).
- Deep links are built with the protocol of `NEXT_PUBLIC_SERVER_URL` (https in this repo's `--experimental-https` dev setup). Server-built `http://` links are unreachable against an https-only dev server and previously made every notification click open a **new tab** (the SW's focus check compared an `https` client URL against the `http` payload URL) — the SW now re-anchors the target to its own origin and focuses by pathname.
- Surfaces: queue board (persistent status), commission detail `/queue/[id]` and customer dashboard `/dashboard/commission/[id]` (`cta` — the ask disappears once subscribed). The dashboard commission page is also the deep link payment/finished pushes open, so an opt-in lands exactly where the next update arrives.
- iOS/iPadOS Safari delivers Web Push **only to sites added to the Home Screen** (iOS 16.4+), so iOS shows an "add to Home Screen first" hint instead of a dead enable button. Desktop and Android opt in directly.
- Unsubscribe clears the browser subscription and the stored row (idempotent on the server).
- **Artists** (Phase B): opt in from the admin header toggle — same state machine, key fetched from `/api/push/config`, hidden on the platform host and on iOS Safari (the Home Screen install flow is storefront-only for now).
- **Admin visibility**: the `push-subscriptions` collection itself is hidden from artists (`admin.hidden`, the same shape as Users / Chat Rooms). Both the sidebar (`StudioAwareNav` filters `visibleEntities`) and the dashboard cards (`getNavGroups(..., visibleEntities, ...)`) derive from `getVisibleEntities`, which evaluates the predicate per request, so the rows drop out of an artist's panel while superadmins keep them. The push actions are unaffected (they pass `overrideAccess: true` and an explicit user), and `admin.hidden` is UI-level: a typed URL is still governed by the collection's access control. Pinned by `tests/int/artist-admin-visibility.int.spec.ts`.

## Host & route-policy integration

`src/proxy.ts` matcher excludes `sw.js`, `manifest.webmanifest`, `apple-icon.png`, and Safari's legacy probes `apple-touch-icon.png` / `apple-touch-icon-precomposed.png`. Without this, these single-segment paths are rewritten to the platform host's 404 route by `isPlatformAllowedPath` — service worker registration on `2monke.com` would silently fail. Matcher sources are parsed by `path-to-regexp`, which rejects nested capturing groups (`(-precomposed)?` breaks boot with "Capturing groups are not allowed"); keep names as plain `|` alternatives — `(?!...)` lookaheads are fine. CSP already allows the worker (`worker-src 'self' blob:`) and same-origin manifest. `web-push` is listed in `next.config.mjs` `serverExternalPackages`.

- Local dev + Safari gotcha (found the hard way during this verification): the dev cert must **enumerate the studio subdomains** — Apple's TLS stack does not honor a `*.localhost` wildcard SAN, and `next dev --experimental-https` reuses `certificates/localhost*.pem` as-is. With the default localhost-only cert, Safari treats every `*.localhost` studio host as a certificate-error origin: the top-level page loads after the interstitial, but subresource loads (dev chunks, source maps) fail — WebKit reports source maps as `Cannot load … due to access control checks`, chunks fail with `ChunkLoadError`, and Next's router turns any RSC-fetch failure into a full browser navigation → page reload loop. Fix: `bash scripts/generate-dev-cert.sh` (re-issues the leaf from the local mkcert CA with explicit SANs; verify with `openssl x509 -noout -ext subjectAltName`), restart `yarn dev`, quit Safari once. Verified against Apple's TLS stack: all enumerated hosts validate (`localhost` + the six seeded studio subdomains).
- Follow-up (2026-09-22) — same symptom reported after the cert was re-issued. Three things were checked and two more dev-only contributors were removed in `next.config.mjs`:
  - `@payloadcms/next`'s `withPayload` marks `Sec-CH-Prefers-Color-Scheme` as a **critical** client hint on `/:path*`. `Critical-CH` is an instruction to the browser: re-request a navigation that arrived without the hint. Nothing on the storefront reads that hint (only Payload's admin `getRequestTheme` does), so every storefront load paid for an extra navigation — measured in Chromium by `scripts/probe-client-hints.mjs`: `307` (the retry) → `200`, i.e. two document requests per load. The rule is now re-scoped to `/admin/:path*` by wrapping `configWithPayload.headers`. Verified: storefront document `200` with no `Accept-CH`/`Critical-CH` and **one** document request per load, while `/admin` still sends both, and `/queue/<id>` still renders as the studio artist in Chromium and WebKit.
  - Correction to the first guess about that header: Safari does **not** loop on it. `scripts/probe-safari-critical-ch.mjs` serves two loopback HTTPS origins with the dev cert — one with `Accept-CH` + `Critical-CH`, one without — and real Safari (26.6.2, safaridriver) requested the document exactly **once** on each. So scoping the hint is a navigation-count fix (real for Chromium), not the cure for the Safari reload loop.
  - The dev config sent `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`, which pins every `*.localhost` studio subdomain to HTTPS inside the developer's browser for a year and makes any cert gap unrecoverable (HSTS cannot be downgraded, so a host with a bad cert is simply dead). It is now production-only.
  - `scripts/generate-dev-cert.sh` now derives its hostnames from `studios.subdomain` (psql + `DATABASE_URL`) instead of a hand-maintained list, so a newly created studio cannot silently fall outside the cert; `--print` shows the SANs without touching `certificates/`.
  - Still unattributed: `InvariantError: Route "/queue/[id]" did not produce a static shell and Next.js was unable to determine a reason. This is a bug in Next.js.` appeared twice in the cold-compile window of the affected session (Next 16.2.12, `cacheComponents: true`; `dynamic-rendering.js` `prelude === 1` with no recorded dynamic usage) and never on warm requests. `next-development.log` is truncated on every dev-server boot, so chasing it needs a fresh cold-start capture.
  - **Push opt-in dead end (2026-09-22), reported right after the loop**: the bar said *"Notifications are blocked for this site. Allow them in your browser settings"* with **no action button**, and `usePushSubscription` read `Notification.permission` exactly once per mount — so a visitor who allowed the site in browser settings stayed blocked with nothing to click. Now: the copy names the settings path (Safari → Settings → Websites → Notifications, plus the Private-window caveat), the state offers **Reload and check** (a reload is the one action that re-reads a settings change with any guarantee), and the hook re-runs detection on `focus`/`visibilitychange` — guarded by a run id and a busy flag so a re-check can never race a subscribe in flight. Tests: `tests/int/push-subscribe-bar.int.spec.ts` 8/8 (3 new) and the push suite 25/25. Verified in a real browser: the blocked state renders the new copy and button; **not** verified there: the granted→ready leg, because headless Chromium cannot grant notification permission at all (`Browser.setPermission('granted')` via CDP leaves `Notification.permission === 'denied'`, see `scripts/probe-chromium-notification-permission.mjs`), so that transition rests on the jsdom spec. If a Safari visitor still reads blocked after reloading, the two things to check are that the allowed entry is the exact origin (`2monke.localhost:3000`, not `localhost:3000` — separate entries) and that the page is not inside a cross-origin frame (the admin live preview), where a frame cannot request notifications.
  - **Reload storm on /queue/<id> — diagnosed 2026-09-22 as a development-only Next.js dev-client behaviour, not an app bug.** Forensics (proxy `[REQ]` lines, `scripts/analyze-req-log.py`): 133 document navigations in 20 minutes to the same URL, `dest=document`, `mode=navigate`, **`auth=cookie`**, `anonPreview=-`, and `referer=` that same URL — i.e. the visitor's session is fine and nothing in the app redirects; the browser is reloading the document ~4–5×/s. The culprit is in the served dev runtime: `function wasServedFromCache() { return performance.getEntriesByType('navigation')[0]?.transferSize === 0 }` and then, for an initial document load, `if (!requestHeaders && wasServedFromCache()) { const readable = restoreDebugChannelFromSessionStorage(requestId); if (readable) return { readable }; /* Debug channel can't be restored — debug deps would block hydration. */ location.reload(); … }`. So: a **cache-revalidated document** (Next serves dev documents with `no-cache, must-revalidate`, which permits a 304 reuse) carries a `self.__next_r` request id whose `sessionStorage` debug-channel entry has already been consumed/deleted → Next reloads to “force a fresh page load from the server” → the browser serves the same cached document with the same stale id → storm. It is tab-local and dev-only: production ships no debug channel, and fresh tabs/profiles never hit it (every Chromium/WebKit/driven-Safari probe here loads the page in one navigation, i.e. `transferSize > 0`). **Remedy:** in the affected tab, Empty Caches (⌥⌘E) / “Reload Page from Origin” (⇧⌘R) / close the tab — the document then comes from the network and the restore path is skipped. **Not fixable from the repo:** `Cache-Control: no-store` for dev documents was attempted in both `next.config.mjs` `headers()` and the proxy response, and Next's page handler overwrites both (curl still shows `no-cache, must-revalidate`); there is no config or env switch for the debug channel (`setReactDebugChannel && createDebugChannel()` in `app-render.js`, no `debugChannel` key in the config schema). Both attempts were reverted. Forensics: the per-request `[REQ]` logger is back behind `DEBUG_REQUEST_LOG=1`; the two low-volume pivot logs (`[GUARD]` in `lib/dashboard-guard.ts`, `[LOGIN]` in the studio login page) stay on in dev.
  - Not verified: the loop itself was never reproduced here — every Chromium and WebKit (Playwright) probe against the same server and cert rendered `/queue/<id>` cleanly — so the Safari-side trigger could not be confirmed locally. After the user enabled Safari's "Allow Remote Automation", real Safari was driven through safaridriver and WebDriver BiDi (`scripts/probe-safari-live.mjs`; Safari's BiDi endpoint is its own port, `ws://127.0.0.1:8099/session/<id>`, and it needs `safari:experimentalWebSocketUrl` alongside `webSocketUrl`): a single `navigationCommitted`, no reload loop over 25s, all 62 dev chunks loaded including the two that failed in the report, no console error entries, and `performance.now()` never reset.
  - The decisive caveat, measured with `scripts/probe-safari-profile.mjs`: Safari's WebDriver session runs in an **isolated profile** — no cookies, no localStorage, no service worker, no cache. Clean results there therefore say nothing about the user's own profile, and the loop kept happening in it after these fixes landed (14:50–14:51: 234 + 92 document requests to the same URL; 326 `ChunkLoadError`s for the same two chunks around 14:55, from the dev log that had been truncated at the config reload — i.e. after it).
  - What that profile's cache had collected: `/ _next/static/**` responses used to carry Payload's `Accept-CH: Sec-CH-Prefers-Color-Scheme`, `Critical-CH: Sec-CH-Prefers-Color-Scheme` and `Vary: Sec-CH-Prefers-Color-Scheme` (its rule lives on `/:path*`, so static assets included; `Vary` on every cached asset also fragments production CDN caches for no benefit). Post-fix those responses are `Vary: Accept-Encoding` only — verified by curl — so new poisoned entries cannot be created, but already-cached ones survive until the browser's cache is emptied. Both `%5B…%5D`-encoded and raw-bracket chunk URLs return 200, so the URL form is not the failure either.
  - HAR analysis (`scripts/analyze-har.py`, `scripts/analyze-loop-window.py`): the loop is **document navigations**, not failed assets. In the user's 17-second capture the dev stylesheet chunk was requested **58 times** (one per navigation, every ~290 ms, every one `200`, `cache: {}` = network loads) while the "failing" JS chunk `[root-of-the-server]__1jlkoby._.js` returned `200` on all 6 requests it appeared in — and `hmr-client…_1qo3276._.js` was never requested at all. The dev server logged only `/queue/<id>` requests during those bursts (326 in 2 minutes, in 2–3 ms pairs) with no API traffic, so the reload is neither fetch-driven nor a redirect chain.
